# 通知

`rajikura serve` は、録音の結果や異常を通知として DB に 1 件ずつ書き、通知先があればそこにも送る（[ADR 0010](adr/0010-per-event-notifications-and-metrics.md)・[ADR 0011](adr/0011-notifications-written-to-db-then-delivered.md)）。DB の通知は、Web UI の通知の画面と帯にも出る（[web-ui.md の「通知の画面と帯」](web-ui.md#通知の画面と帯)）。用語は [GLOSSARY.md](../GLOSSARY.md) に従う。

## 通知先

Web UI の設定の画面の「通知」か、`PATCH /api/settings` の `notify` で変える（[settings.md](settings.md)）。保存したら、再起動しなくても新しい通知先に送る。

- 通知先（`channel`）は 1 つだけ選ぶ。
  - `discord`: Discord の Webhook に送る。
  - `slack`: Slack の Incoming Webhook に送る（Bot token は使わない）。
  - `email`: SMTP でメールを送る（下の「[メール](#メール)」）。
  - `none`: 通知先なし。DB に書くだけで、どこにも送らない。
- 何も保存していなければ `none`。
- 通知先の設定（`discord_webhook`・`slack_webhook`・`notify.smtp`）を書いたのに `channel` を書かず、今の通知先が `none` なら、何も当てずにエラーにする（書き忘れで通知が黙って止まらないように）。
- 今の通知先が `discord` などなら、`channel` を書かずに Webhook の URL だけを入れ替えられる。`channel` に選んだ通知先の設定が無いときは、エラーにする。
- Webhook の URL と SMTP のパスワードは秘密（[settings.md の「秘密」](settings.md#秘密)）。起動時のログには、通知先の種類（`notify=discord` など）だけを出す。
- `notify.success` が `false` なら、録音済みの通知を通知先に送らない（Web UI の履歴には残る）。ほかの通知は止められない。
- Discord の 1 通の上限（2000 文字）と、Slack の上限（4000 文字）を超える本文は切り詰め、切り詰めたことを本文の末尾に書く。

## メール

`channel` が `email` のときは、`notify.smtp` の `host`・`port`・`username`・`from`・`to`・`password` が全部要る。足りなければ、足りないものを挙げてエラーにする。`from`・`to` がメールアドレスの形に読めない、`port` が 1〜65535 でないときもエラーにする。

- TLS は必須で、平文では送らない。ポートが 465 なら最初から TLS、それ以外のポート（587 など）は STARTTLS を必須にする。サーバーの証明書も確かめる。
- `username` とパスワードで PLAIN 認証する。
- 件名は通知の種類から作る（`[rajikura] 録音済み`・`[rajikura] 録音できなかった` など）。本文は通知の本文のまま（プレーンテキスト）。
- `to` が複数なら、1 通のメールを全員宛てに送る。
- 1 通を送る時間の上限は 30 秒。

`PATCH /api/settings` の本文の例（Gmail）:

```json
{"notify": {"channel": "email", "success": true, "smtp": {"host": "smtp.gmail.com", "port": 587, "username": "you@gmail.com", "from": "you@gmail.com", "to": ["you@gmail.com"], "password": "<アプリ パスワード>"}}}
```

Gmail では、Google アカウントで 2 段階認証を有効にし、「アプリ パスワード」を作って `password` に書く（通常のログインのパスワードは使えない）。`port` は `587`（STARTTLS）か `465`（最初から TLS）。

## 送り方

- 通知を作る処理は DB に書くだけ。通知先には、録音のループの周（1 分ごとと、人の操作で起こされたとき）で、まだ送れていない通知を古い順に送る。
- 送れなければ、次の周でまた送る。作ってから 1 時間を過ぎた通知が送れなかったときは、諦めて「送れなかった」の印を付ける（[api.md の `/metrics`](api.md#メトリクスget-metrics) の `rajikura_notify_failures_total` が数える）。
- `serve` が止まっていた間に 1 時間を過ぎた通知も、起動後に通知先が動いていれば送る。
- 通知先が `none` の間に作った通知は、後で通知先を選び直しても送らない。
- 通知を書いたら、本文をログ「通知を書いた」にも出す。DB に書けなければ、エラーと本文をログに出す。どちらでもジョブの処理は止めない。
- 通知の行は 90 日で消す。ただし、まだ復旧していないサービスの異常の始まりの行は消さない。
- テスト通知だけは周を待たず、人が送ったその場で通知先に送る（送り直さない）。送り方は [web-ui.md の「テスト通知」](web-ui.md#テスト通知)。

## 通知の種類

通知の源は、ジョブの出来事・キーワードの出来事・番組の出来事・サービスの異常・テスト通知の 5 つ。本文の頭に印を付ける。 <!-- 足したら直す: 通知の種類 -->

| 通知 | 頭の印 | いつ書くか | 重複の防ぎ方 |
| --- | --- | --- | --- |
| 録音済み | 【録音済み】 | 欠落なしで保存したとき | 要らない（保存は 1 度。[録り直し](cli.md#rerecord)で録れたら、もう 1 度書く。[チャプターの取り直し](settings.md#チャプターの取り直し)では書かない） <!-- 足したら直す: 通知の種類 --> |
| 欠落あり | 【欠落あり】 | 欠落ありで保存したとき（`done` だが欠落がある） | 同上 |
| 録音できなかった | 【録音できなかった】 | ジョブが `expired` になったとき（[ライブ録音](recording.md#保存のやり直し)で録れた分を保存できなかったときは、保存のやり直しを打ち切ったとき） | 要らない（状態が変わったときに 1 度書く。手動再試行か録り直しの後にまた `expired` になれば、もう 1 度書く） <!-- 足したら直す: ジョブの状態の移り方 --> |
| 録らない予定にした（`skip_planned`） | 【録らない予定】 | 最初の試行の時刻の前に、番組名が食い違うので、録音予定のジョブを録らない予定にしたとき（[shows.md の「番組名の確かめ」](shows.md#番組名の確かめ)） | 要らない（状態が変わったときに 1 度書く。番組名が行き来すれば、そのたびに書く） |
| 録音予定に戻した（`unskipped`） | 【録音予定に戻した】 | 番組名が直ったので、録らない予定のジョブを録音予定に戻したとき | 同上 |
| 録らなかった（`skipped`） | 【録らなかった】 | 今日より前の放送回で番組名が食い違うので、ジョブを録らなかったで作ったとき、または最初の試行の時刻に取り直した番組表で番組名が食い違うので、録音予定のジョブを録らなかったにしたとき。録らない予定のジョブがそのまま確定したときは書かない（録らない予定で知らせた） | 要らない（ジョブにつき 1 度） |
| 期限間近 | 【期限間近】 | 録音期限の 24 時間前を過ぎても、`done` / `expired` / `skipped` でないジョブ。ライブ録音のジョブと、チャプターの取り直しのジョブには書かない | ジョブごとに 1 度 <!-- 足したら直す: ジョブの状態の移り方 --> |
| キーワードで録音予定（`keyword_added`） | 【キーワードで録音予定】 | [キーワード](shows.md#キーワード)に当たった放送回を、番組の 1 回の予約として足したとき。分割番組のパートをまとめて足したときは 1 通 | 要らない（足した放送回は記録に残り、もう足さない） |
| キーワードの上限（`keyword_limit`） | 【キーワードの上限】 | キーワードが上限（`keyword_max_pending`）に達して、当たった放送回を足さなかったとき | 上限を下回るまで書かない（下回ってから、また達したら、もう 1 度書く） |
| 当たらない日（`unmatched_day`） | 【当たらない日】 | 番組表の同期（か番組を変えた直後の展開）で、まだ通知していない当たらない日（[web-ui.md の「番組の画面」](web-ui.md#番組の画面)）を見つけたとき。同期 1 回・番組ごとに 1 通にまとめる | 当たらない日ごとに 1 度。直ったときは書かない |
| 番組表の同期の失敗 | 【番組表の同期の失敗】 | 番組表の同期が 2 回続けて失敗したとき | 異常が続いている間（始まりがあって復旧が無い間）は書かない |
| エリア外 | 【エリア外】 | radiko がエリア外と判定したとき | 同上。ジョブは試行の失敗として再試行を待つ |
| バックアップの失敗（`backup`） | 【バックアップの失敗】 | 自動のバックアップを取れなかったとき（[backup.md の「自動のバックアップ」](backup.md#自動のバックアップ)） | 同上 |
| スリープから起こせない（`wake`） | 【スリープから起こせない】 | Windows で、ライブで録るジョブの前にスリープ中の PC を起こせないと分かったとき（[windows.md の「起こせないと分かったときの警告」](windows.md#起こせないと分かったときの警告)）。本文に、対処を書いた節と理由を添える | 同上。理由が変わっても始まりは 1 回だけ |
| 再スキャンの失敗（`rescan`） | 【再スキャンの失敗】 | 保存の後にライブラリの再スキャンを頼めなかったとき（[settings.md の「ライブラリの再スキャン」](settings.md#ライブラリの再スキャンjellyfin)）。本文に、対処を書いた節とエラーを添える | 同上 |
| 復旧 | 【復旧】 | 続いていたサービスの異常が直ったとき（下の箇条） | 続いている異常にだけ書く <!-- 足したら直す: サービスの異常 --> |
| テスト通知 | 【テスト】 | 人が Web UI かトレイ（か API）でテスト通知を送ったとき | 要らない（押すたびに 1 通） |

復旧を書くとき: <!-- 足したら直す: サービスの異常 -->

- 番組表の同期: 失敗が続いている間に、同期が成功したとき。
- エリア外: 続いている間に、radiko の認証が通ったとき。
- バックアップの失敗: 取れない間に、次のバックアップを取れたとき。取る先（`backup_dir`）を空にして自動のバックアップを止めたときも、次の見回りで書く。
- スリープから起こせない: 次にライブで録るジョブの分のタイマーを、起こせる見込みで掛けられたとき（[windows.md の「起こせないと分かったときの警告」](windows.md#起こせないと分かったときの警告)）。
- 再スキャンの失敗: 次に再スキャンを頼めたとき。頼む先が無くなった（`jellyfin.url` を空にしたか、API キーを復号できない）ときも、次の見回りか保存のときに書く。

ほかに:

- 再試行待ちになっただけでは通知しない（録音期限が近づけば期限間近が出る）。 <!-- 足したら直す: ジョブの状態の移り方 -->
- サービスの異常が続いているかは、DB の通知から判定する。再起動しても、続いている異常の始まりを送り直さない。
- 番組表の同期は、どの局・放送日の番組表も取れなかったとき、または DB を読めなかったときに失敗とみなす。一部だけ取れなかったときは失敗とみなさない。
- 録らない予定にした・録音予定に戻した・録らなかったは、rajikura が番組名で決めたときだけ書く。人が「録らない」「録る」を選んだときは書かない。
- キーワードの出来事と番組の出来事は、`notify.success` が `false` でも通知先に送る（`success` が止めるのは録音済みだけ）。

## 本文

例の `○○` は番組の名前。

- 録音済み: 1 行（例: `【録音済み】○○・放送日 2026-10-14（42 分）`。分は保存したファイルの長さ）。
- 欠落あり: ジョブと、放送回の数のうち欠落した数と、保存先と、欠落した放送回を 1 行ずつ（局・時刻・番組名）書く。ライブ録音のジョブでは、欠けた長さの合計と、欠けた区間を 1 行ずつ書く（例: `【欠落あり】○○・放送日 2026-10-20 を、ライブ録音で録れた分だけで保存した（欠けた長さ 合計 1 分 30 秒。放送回 1 件のうち 1 件に欠落）。`）。
- 時刻は、放送回の放送日の時刻で書く（深夜 1 時は `25:00`。[ADR 0012](adr/0012-airing-time-in-broadcast-day-time.md)）。
- 録音できなかった: ジョブと試行の回数と録音期限を書き、直近のエラーを添える（例: `【録音できなかった】○○・放送日 2026-10-14 を録音できず、expired にした（試行 7 回、録音期限 2026-10-14 21:35）。` と `直近のエラー: [save] …`）。
- ライブ録音で録れた分を保存できずに打ち切ったときは、録れた分を残した場所と消す日時と、原因を直してから `rajikura retry <ID>` か、ジョブの画面の「手動で再試行」で保存からやり直せることを添える。
- ライブ録音で、保存した長さが全セグメントの長さの合計と 10 秒を超えてずれたまま保存したときは、録音済みか欠落ありの最後にずれを 1 行添える。
- ライブ録音のジョブが同時に録る本数の枠待ちだったときは、欠落ありか録音できなかったの最後に、枠待ちの 1 行を添える（[recording.md の「ライブ録音」](recording.md#ライブ録音)）。
- 録音済みと録音できなかったには、番組名の食い違いを 2 行目に添える（例: `番組名の食い違い: 番組表の番組名 「…」 が番組の name で始まらない`）。比べ方は [shows.md の「番組名の確かめ」](shows.md#番組名の確かめ)。`check_title` を `false` にした番組は対象にしない。
- キーワードで録音予定: キーワードの語・番組名・放送日と時刻と局・足した先の番組の名前・番組を新しく作ったかを書く（例: `【キーワードで録音予定】キーワード「会議室」に当たった「サンプル 夜の会議室(1)」（放送日 2026-10-14 22:00〜24:00 サンプル局）を、番組「サンプル 夜の会議室」に足した（2 パートをまとめて）。番組「サンプル 夜の会議室」は新しく作った。`）。
- 分割番組でない（`split` が `"none"`）既存の番組が、足した後に、同じ放送日に 2 つ以上の放送回を当てるときは、パートごとに別のファイルになることを添える。
- 当たらない日: 1 行目に番組の名前を、2 行目から当たらない日ごとに 1 行ずつ書く（例: `【当たらない日】番組「○○」の毎週の予約の枠に、番組表の放送回が無い日がある（録音しない）。` と `- 10/19（月）17:40 は放送回が無い。その時刻は「サンプル 夕方の特番」（15:30〜18:00）。番組名の合う放送回: 19:00〜19:30`）。
- 録らなかった: ジョブと録音期限と、録るなら「録る」を選ぶことを書き、2 行目に番組名の食い違いを書く。
- 録らない予定: ジョブと録りにいく時刻（最初の試行の時刻）と、録るなら「録る」を選ぶことを書き、2 行目に番組名の食い違いを書く。録音予定に戻したは 1 行。
