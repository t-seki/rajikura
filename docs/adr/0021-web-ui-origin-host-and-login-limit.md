# Web UI はオリジンと Host を確かめ、ログインの失敗を全体で数える

## 決定

Web UI の守りに、cookie の `SameSite=Strict` のほか、ブラウザ経由の攻撃（ほかのオリジンからの要求と DNS rebinding）への手当てと、ログインの総当たりの制限を持たせる。どれも `serve` の中で行い、起動の設定は `-allowed-hosts` だけを持つ。

- ほかのオリジンからの要求: Go の標準の `http.CrossOriginProtection` を、`/api/` の GET・HEAD 以外のすべての要求に掛ける（`/api/` に OPTIONS の口は無い）。ログインする前の `POST /api/login`・`POST /api/setup` も含む。`Sec-Fetch-Site` も `Origin` も付けない要求（CLI など、ブラウザのほか）は通す。断ったときは 403。
- `Host`: 通すのは、IP のアドレス（v4・v6）、`localhost`、`serve` の `-allowed-hosts` に並べた名前だけ。名前は大文字小文字を区別せず、ポートは見ない。掛けるのは `/api/` と SPA で、`/healthz`・`/metrics` には掛けない。断ったときは 421 で、`-allowed-hosts` に足すよう返し、ログに断った `Host` を出す。
- ログインの総当たり: 接続元を区別せず、全体で数える。5 回続けて間違えたら 1 分受け付けず、その後も間違えるたびに止める時間を倍にする（上限 15 分）。成功したら 0 に戻す。止めている間は、正しいパスワードも 429 で断る。`PUT /api/password` の今のパスワードの間違いも、同じ数に入れる。回数は `serve` の中にだけ持ち、起動し直すと 0 に戻る。
- セットアップコードの制限（5 回続けて間違えたら次の起動まで受け付けない。[ADR 0016](0016-first-password-by-setup-code.md)）は別に持つ。

## 理由

- DNS rebinding は、攻撃者のドメイン名を 127.0.0.1 や LAN の IP に向け直す攻撃で、要求の `Host` は攻撃者のドメイン名になる。IP のアドレスの `Host` はこの攻撃では来ないので、無条件で通しても守りは弱まらず、LAN の IP で開く人と、IP のアドレスで叩く死活監視に設定が要らない。
- `SameSite=Strict` は、同じサイト（例: `*.example.com` のほかのアプリ）からの要求には cookie を送る。オリジンの検査は、それに頼らない守りになる。
- 利用者は 1 人で、リバースプロキシの後ろでは接続元の IP がどれもプロキシに見える。全体で数えれば、プロキシの設定に依らずに効く。
- 許す名前を DB の設定に置くと、名前を許す前は名前で開けず、最初のセットアップで回り道が要る。`-listen` と同じ起動の設定に置けば、起動の時点で決まる。

## 検討した案

- CSRF トークン（cookie とヘッダに同じ値を載せる形など）。SPA にトークンを読んで付ける処理が要り、標準の検査で足りる。
- `Origin` を自前で比べる。標準に同じものがある。
- `Host` を、待ち受けのアドレスに合う IP と許した名前だけにする。`:8080`（全部のアドレス）のときに何を許すかが決めにくく、コンテナの IP も変わる。
- ログインの失敗を接続元の IP ごとに数える。プロキシの後ろでは効かず、`X-Forwarded-For` を信じるには、信じるプロキシの設定が要る。
- 失敗のたびに一定の時間待たせるだけ。並行に叩かれると効かない。
- 許す名前を DB の設定（Web UI）か環境変数に置く。DB は上の理由で採らない。起動の設定はフラグに揃える。

## 帰結

- 攻撃者がログインを間違え続けると、持ち主も新しくログインできなくなる。今のセッションと API トークンはそのまま使え、`serve` を起動し直せば戻る。
- 名前で開く構成（リバースプロキシの経路、VPN の名前解決など）では、`-allowed-hosts` にその名前を足す。
- Windows の `service install` は `-allowed-hosts` を渡さない。LAN からは IP のアドレスで開く（[ADR 0020](0020-windows-service-with-virtual-account.md)）。
