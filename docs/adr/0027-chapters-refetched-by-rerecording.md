# チャプターはタイムフリーからの録音の保存のときに取り、取れなければできるのを待って録り直して入れる

## 決定

radiko は、タイムフリーの番組に AI が作るチャプター（話題・場面ごとの区切り。時刻・題・種類、音楽なら曲名とアーティスト）を付けている。聴くときに話題や曲に飛べるよう、タイムフリーから録るファイルにこれを埋め込む。録音は遅らせずに録って保存し、チャプターが取れなかった放送回は、後でできたかを確かめ、できていれば rajikura が録り直してファイルに入れる（チャプターの取り直し）。

取り方と形:

- 取り先は `https://api.annex-cf.radiko.jp/v1/programs/{eventId}/chapters`（認証なし）。`eventId` は `/v1/programs/list` を局と放送日で引き、放送回の開始時刻で照らして決める（分割番組のパートは `-1` などの枝番を持ち、v3 の番組表の `prog id` では引けない）。公開の文書の無い API なので、予告なく変わりうる。
- 形は、Nero の `chpl` と QuickTime のチャプタートラックの両方（ffmpeg の既定と同じ）。`muxer` が `ffmpeg` でも `builtin` でも同じ形にする。
- 分割番組をつないだファイルは、パートごとに取り、ファイルの中でのそのパートの始まりだけ時刻をずらす。
- 設定 `chapters`（既定はオン）は、チャプターを取り、取れなければ取り直すかを決める。オフなら取らないし、取り直しもしない。ライブ録音のファイルには入れない。

取り直し:

- タイムフリーから録るジョブの最初の試行は、`chapters` に関係なく、最後の放送回の終了 + max(局の `tf_max_delay`, 150 秒) + 2 分にする。
- 保存のときに、チャプターが 404 か通信の失敗で取れなかった放送回があれば、ジョブは録音済み（`done`）のまま、チャプターを待つ。空（200 で 0 件）と、放送回の一覧に eventId が無いときは待たない。
- 待っているジョブは、録音のループが、チャプターの API だけを保存から 30 分おきに引く。最後の放送回の終了から 6 時間で打ち切る。間隔と打ち切りは設定にしない。
- 待っていた放送回が全部取れるようになったら（打ち切りの時点で一部だけ取れるようになっていれば、そのとき 1 回）、録り直し（[ADR 0025](0025-rerecord-done-job-separately-from-manual-retry.md)）と同じく、試行回数 0 で次の試行を今にし、どの放送回も radiko から取り直して保存する。前の保存先と同じ名前なら上書きし、再スキャンする。
- チャプターの取り直しで起こした試行が尽きたら（録音期限の時点で一部の放送回しか取れなかったときも）、録音済みに戻す。前のファイル、保存先、欠落の印は前のまま残す。
- チャプターの取り直しは、録れても録れなくても通知しない。
- 人が録り直しをしたら、待ちを消す。保存のたびに待つかを決め直す。API を引くときに `chapters` がオフなら、待ちを消す。録音期限を過ぎたら打ち切る。
- ジョブには、チャプターが入ったか（入った・待っている・入らなかった）を持たせ、ジョブの一覧と詳細に出す。Web UI の一覧には、待っているジョブに「チャプター待ち」、入らなかったジョブに「チャプターなし」の印を出す。取りに行っていないジョブ（ライブ録音、設定がオフなど）には値を持たせない。入らなかったは、打ち切ったときと、待たない理由で取れなかったとき（一部だけ入ったときも含む）。

## 理由

- チャプターができるまでの時間は回によって違い、番組の終了から 1 時間前後でできる回もあれば、90 分を過ぎてもできていない回もあった。最初の試行を遅らせる値では取りこぼしを無くせない。後で取り直せば、できるまでの時間を決め打たなくてよい。
- 取り直しがあれば、最初の試行を遅らせる理由が無い。タイムフリーの録音は終了の数分後に聴け、チャプターの無い局（NHK など）の録音も遅れない。
- まだ無いのか、局に無いのかは、応答で見分けられない。待っている間は API を 1 本引くだけにし、音声を取り直すのはチャプターができてからにする。打ち切りで止める。
- ファイルの書き直しを、録り直しの試行に任せる。録り直しなら、partial に書いて rename で確定する保存（メディアサーバーやプレイヤーが書きかけを読まない）、前の保存先の上書き、一部しか取れなかったときに前のファイルを残す決まりが、そのまま効く。
- ジョブを録音済みのまま待たせ、取り直しの試行が尽きても録音済みに戻すのは、録音は済んでいて聴けるファイルがあるため。録音できなかったと表示・通知すると、事実と違う。
- 通知しないのは、録音の結果は 1 回目の通知で伝わっており、チャプターの有無は人に何かしてもらう出来事ではないため。チャプターの無い局では毎回打ち切りになるので、打ち切りを通知すると、その局の番組のたびに通知が増える。
- 両方の形を書けば、ffmpeg 版と builtin の箱がそろい、箱を比べるテスト（[ADR 0013](0013-builtin-m4a-muxer.md)）を保てる。読み手は、media3（1.11 から両方）、ffmpeg・ffprobe・mpv（両方）、VLC（両方）。Apple の製品はチャプタートラックだけを読むと言われる（確かめていない）。
- Jellyfin（v12.3 まで）は、音楽ライブラリの Audio のチャプターを保存しない（AudioBook だけ）。音楽ライブラリのまま（[ADR 0002](0002-jellyfin-preset-layout.md)）、ファイルの中のチャプターを、ファイルをそのまま読むプレイヤーで使う。

## 検討した案

- 最初の試行を番組の終了の 90 分後まで遅らせ、保存のときに 1 回だけ取る。音声を 2 回取らずに済むが、90 分を過ぎてもできていない回を取りこぼし、チャプターの無い局の録音まで毎回 90 分遅れる。
- 最初の試行を遅らせ、取れなかった放送回だけ取り直す。音声を 2 回取るのはまれになるが、チャプターの無い局の録音が毎回遅れる。タイムフリーの録音をすぐ聴ける方を取った。
- 保存済みの m4a を読み、チャプターを足して書き直す。音声を取り直さずに済むが、builtin の muxer（ADTS だけを読む）に m4a を読む部品が新しく要る。
- 作業用フォルダ（ADTS）を残し、チャプターができたら保存し直す。待っている間のディスクと、残す・消す決まりが増える。
- 取り直しの打ち切りを通知する。チャプターの無い局の番組のたびに通知が届く。
- 待っている間を新しいジョブの状態にする。番組表・Web UI・API の状態の場合分けが全部広がる。
- 遅らせない局（チャプターの無い局）の一覧を持つ。radiko は公表しておらず、裏付けの無いまま古くなる。
- `chpl` だけを書く。builtin は箱 1 つで済むが、ffmpeg 版と形がそろわず、Apple の製品で読めない。
- 別のファイル（`.cue`・`.json`）に書く。プレイヤーが m4a と組で読まず、ライブラリにファイルが増える。

## 帰結

- チャプターのある局では、ほぼ全部の放送回で音声を 2 回取り、ファイルを 2 回書き、再スキャンも 2 回になる。録音が非会員の聴取制限に数えられるかは確かめていない（[要件定義の「未確認の事項」](../requirements.md#未確認の事項)）。困ったら `chapters` をオフにすれば、取るのは 1 回に戻る。
- 終了の数分後に置かれたチャプターの無いファイルは、後でチャプター付きのファイルに置き換わる（同じパス）。先にファイルを取り込んだプレイヤーが置き換わりに追いつくかは確かめていない。
- チャプターの取り直しの試行の間（数分）は、ジョブが再試行待ち・録音中になり、番組表には録音予定と出る。
