# 設定と秘密は DB に置き、起動の設定はフラグだけにする

## 決定

設定（保存先・通知先・Jellyfin・ffmpeg のパスなど）は DB にだけ置き、人は Web UI で変える。API トークンを持つスクリプトや AI は `GET` / `PATCH /api/settings` で変える。設定ファイルと、秘密を渡す環境変数は持たない。DB を開く前に要る起動の設定は、`serve` のフラグ `-data`（データのフォルダ）・`-listen`・`-allowed-hosts`（[ADR 0021](0021-web-ui-origin-host-and-login-limit.md)）だけにする（ほかに、パスワードを戻す `-reset-password` がある。[ADR 0016](0016-first-password-by-setup-code.md)）。

- データのフォルダには、DB・秘密の鍵のファイル・作業用フォルダ・セットアップコードのファイルを置く。既定は実行ファイルと同じフォルダで、コンテナの既定の引数は `-data /data serve`。`-listen` の既定は `:8080`。
- 秘密は、DB の中では暗号化し、鍵はデータのフォルダの別のファイルに置く。Web UI・API は、秘密の値を返さず、設定済みかどうかだけを返す。鍵のファイルが無い・合わないときも、起動は続ける。復号できない秘密は未設定として扱い、Web UI とログで知らせる。
- 設定は、保存したら再起動しなくてもすぐに効く。走っている録音は、始めたときの設定のまま最後まで進める。起動の設定は再起動が要る。`radiko.program_cache_mb`（番組表のキャッシュの大きさ）は例外で、キャッシュは起動したときの値で作るので、変えたら再起動が要る。
- radiko のホストは、人の使う設定に置かない。テストが偽の radiko を差すための口は、`serve` に渡す起動の設定の型にだけ置く（フラグは作らない）。
- 設定や番組をファイルで受け渡す口は持たない。DB を移すときはバックアップを使う（[ADR 0017](0017-backup-by-db-copy.md)）。

## 理由

- 主に使う人として、市販のラジオ録音ソフトから乗り換える Windows の人を先にする。その人たちにとって、設定ファイルを手で書くことと、Windows のサービスに環境変数を渡すことは手間になる。
- 入口を DB 1 つにすれば、「この値はどこで決まっているのか」を画面と docs で説明しなくて済む。
- 秘密を暗号化しておけば、DB のファイルだけが外に出たとき（バックアップ、調べるために写したとき）に秘密が読まれない。radiko のパスワードは送り直す必要があり、hash にはできない。
- 起動の設定は DB の場所と待ち受けるアドレスなどだけなので、そのためだけに設定ファイルとその場所を決めるのは手間なだけになる。DB・鍵・作業用フォルダが 1 つのフォルダにそろうので、移すときもフォルダを写せば済む。

## 検討した案

- 設定ファイルと環境変数に書いた値を DB より優先し、Web UI では変えられないようにする。コンテナの設定を宣言的に書けるが、入口が 2 つになる。
- 設定ファイルを正本にし、Web UI でそのファイルを書き換える。Windows のサービスの書き込みの権限や、読み取り専用でマウントした設定とぶつかる。
- 秘密を平文で DB に置く。DB のファイルが外に出たときに読まれる。
- OS の鍵の仕組み（Windows の DPAPI など）で秘密を守る。OS とサービスのアカウントに縛られ、コンテナでは使えない。
- 保存した後に、人に再起動してもらう。Windows の人にサービスの再起動を頼むことになる。

## 帰結

- PC を乗っ取られたとき（鍵のファイルも読まれたとき）は、秘密を守れない。
- 鍵のファイルを失うと、秘密を入れ直すまで、通知先・Jellyfin などは秘密を要しない形でしか動かない（通知は Web UI の履歴にだけ残る）。DB を移すときは、鍵のファイルも一緒に写す。
