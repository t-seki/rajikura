# 通知はまず DB に書き、通知先には別に送る

## 決定

通知を作る処理は、通知を DB の 1 行として書くだけにする。通知先（Discord・Slack・メール）には、録音のループの周（1 分）ごとに、まだ送れていない行を古い順に送る。作ってから 1 時間送れなければ諦め、「送れなかった」の印を付ける。DB の行は、そのまま Web UI の通知の履歴になる。

テスト通知だけは例外にする。

- 人が押したその場で、Web UI の側から通知先に送り、送れたか送れなかったかを付けた行として DB に書く。送り直しはしない。
- 送れたテスト通知は、Web UI の「送れなかった通知」の帯を消す条件（最後に送れなかった時刻より後に送れた通知がある）にそのまま数える。送れなかったテスト通知は `rajikura_notify_failures_total` で数えない。
- 通知先なし（`notify.channel = "none"`）のときは、送らずに行だけを書く（送る印も、送れた・送れなかったの印も付けない）。
- テスト通知は Web UI とトレイのメニューから送れる。

## 理由

- 送り直しの工夫が 1 か所にまとまる。通知の種類ごとに「送れたら印を立てる」「取り消されていても送る」をばらばらに持たずに済む。
- 通知先が無い人も、Web UI の履歴で同じ通知を読める。通知先が壊れていても、通知そのものは失われない。
- プロセスが落ちても、送れていない通知は DB に残り、起動後に送られる。
- サービスの異常が続いているかを、通知の行（始まりがあって復旧が無い）から判定できる。再起動しても始まりを送り直さず、Web UI の帯もここから作る。
- テスト通知は「今、通知先に届くか」をその場で知るためのもの。ループの周を待つと結果がすぐ分からず、送れない間は送り直しで行が溜まる。人がその場で失敗を見ているので、送れなかった数にも入れない。
- 通知先なしでトレイを使う人も、テスト通知が履歴に入ってトレイに届くかを確かめられる。

## 検討した案

- 通知を作った場で送る。送り直しが種類ごとにばらばらになり、Web UI の履歴を別に書くことになる。
- 上限なしで送り直す。Webhook が失効していたときに、直した後で溜まった古い通知が一度に届く。
- 送り直さない（1 回だけ試す）。一時的なネットワークの失敗で通知が失われる。
- 通知先なしのときはテスト通知を断る。トレイに届くかを確かめる手段が無くなる。

## 帰結

- 通知の表は 90 日で消す。まだ復旧していないサービスの異常の始まりの行は消さない（帯の元になる）。
- 通知が通知先に届くのは、作ってから最大でループの 1 周（1 分）後になる。
- 送れなかった数は `/metrics` の `rajikura_notify_failures_total` で外から見え（[ADR 0010](0010-per-event-notifications-and-metrics.md)）、Web UI では帯に出る。
