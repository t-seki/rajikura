# CLI は HTTP API を呼び、DB に書くのは serve だけにする

## 決定

`rajikura` の `jobs`・`retry`・`skip`・`record`・`rerecord`・`backup` は DB を開かず、`serve` の HTTP API を API トークンで呼ぶ。DB を開いて書くのは `serve` だけ。DB を直接開くモードは持たない。`version`・`licenses` と、Windows の `service`・`tray`（[ADR 0020](0020-windows-service-with-virtual-account.md)・[ADR 0023](0023-windows-tray-embedded-and-linked-by-loopback.md)）は手元で動く。

- 接続先とトークンは、値ごとに、フラグ（`-url`・`-token`）→ 環境変数（`RAJIKURA_URL`・`RAJIKURA_TOKEN`）→ 設定ファイル（`os.UserConfigDir()` の下の `rajikura/client.toml`。キーは `url` と `token`）の順に、先にあるものを使う。設定ファイルの場所を変えるフラグは作らない。
- 設定ファイルの権限が 0600 より広ければ（Windows のほか）、または接続先が `http://` で localhost のほかなら、警告を出して続ける。暗号化された経路（VPN など）を通す使い方もあるので止めない。
- `serve` が止まっていてつながらないときは、つながらない旨のエラーで終わる。

### 展開役

`serve` の中で、展開（番組表を取ってジョブに当てる処理）は展開役（goroutine 1 本）だけが行う。

- 展開役が順に処理するのは次の 4 つ。
  - Web UI・API からの展開の依頼（番組や予約を変えたとき）
  - その依頼で展開できなかった「局 × 放送日」の試し直し
  - 6 時間ごとの番組表の同期と、起動時の同期
  - 録音の前の番組表の取り直し（最初の試行の直前）。録音のループは取り直しを展開役に頼み、終わるまで待ってから録音する
- 録音のループ（1 分ごとのジョブの実行と通知の判定）は録音だけを担う。録音中も展開役は止まらないので、番組の変更の展開は録音の終わりを待たない。
- 依頼はプロセスの中のキューに積む（DB の表は作らない）。`serve` を再起動すると依頼は消えるが、起動時の同期で拾い直す。
- Web UI・API は展開を待たずに応答を返す（依頼を積んで展開役を起こしたら返す）。

試し直し:

- 試し直すのは、展開できなかった「局 × 放送日」だけ（展開できた放送日は取り直さない）。番組表は「局 × 放送日」ごとに 1 リクエスト。
- 間は延ばしていく: 1 分 → 5 分 → 15 分 → 30 分、以降 30 分ごと。
- 次の番組表の同期が終わったら、その同期より前に積まれた依頼の分のうち、同期が展開できた「局 × 放送日」と、同期の対象でなかった「局 × 放送日」（消した番組・無効にした番組の局、同期が見ない過去の放送日）を捨てる。同期でも展開できなかった分は試し直しを続ける。同期が局・放送日の展開まで進まなかったとき（DB を読めないなど）は何も捨てない。
- 記録はログだけ（DB には残さない）。試し直すたびの Warn に、試し直しの回数と次の時刻を入れる。同期で捨てたときにも 1 行出す。
- 同期の失敗の通知は、2 回続いたときに出す。

## 理由

- CLI を手元のマシンに置いて、別のマシンで動く `serve` を操作できる。AI に操作させるときも、DB のファイルやコンテナの中に触らせずに、API トークンだけを渡せばよい。
- DB に書くプロセスが 1 つなら、番組を変えた後の展開を `serve` の中の 1 か所にまとめられる。CLI が DB に書くと、`serve` は変更を知らないので、展開が次の同期まで遅れる。
- 展開を 1 本の goroutine に限れば、2 つの展開が同時に走らない。
- 試し直しの間を延ばせば、1 局 1 日の番組表が取れないだけで radiko に毎分リクエストを送り続けることが無い（1 分ごとに 8 日分を取り直すと、6 時間で約 2,880 リクエストになる。延ばす形なら約 14）。

## 検討した案

- CLI が DB を直接開き、`serve` との受け渡しを DB の伝言板（展開の依頼の表）で行う。CLI が DB のファイルに届く場所でしか動かず、手元や AI から使えない。DB に書くプロセスが 2 つになる。
- 一部のサブコマンドだけ HTTP で `serve` に頼み、ほかは DB を直接開く。CLI の使い方が 2 通りに分かれる。
- 同期も依頼のキューに入れる。同期の失敗の通知の数え方を作り直す必要があり、番組表を取れない間は 1 分ごとに全局の番組表を取りに行くことになる。
- 同期・見回り・依頼を、録音と同じ 1 本のループで回す。録音の間、番組の変更の展開が待たされる。

## 帰結

- `serve` が止まっている間は、CLI の `jobs` などが使えない。DB を直接開く逃げ道も無い。
- 保存の直後に読み直した画面や `jobs` では、展開がまだ終わっておらず、ジョブがまだできていないことがある。
- 展開できない局・放送日は、同期で展開できるか同期の対象から外れるまで、間を延ばしながら試し直す（30 分ごとに落ち着く）。
- 録音の前の取り直しも展開役に並ぶので、展開役がほかの処理をしている間は、録音の始まりが待たされる。
- `jobs` の一覧（`GET /api/jobs`）は、放送日が今日の放送日の 120 日前以降のジョブだけを読み、直近の試行もそのジョブの分だけを 1 回の問い合わせ（`Store.LatestAttemptsFromDay`）で読む。
