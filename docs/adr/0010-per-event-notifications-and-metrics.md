# 通知は出来事が起きるたびに出し、生存確認は /metrics を外から見る

## 決定

通知は、ジョブの出来事（録音済み・欠落あり・録音できなかった・期限間近など）、キーワードの出来事、番組の出来事、サービスの異常（同期の失敗が続いている・エリア外など、とその復旧）を、起きるたびに 1 件ずつ出す。日ごとのまとめは送らない。

「rajikura が動いていること」と「通知先が壊れていないこと」は、通知が届くことに頼らず、`/metrics`（最後に保存した時刻・通知を送れなかった数）を外の監視（Prometheus など）で見る。

## 理由

- 通知先（Discord・Slack・メール）と Web UI の履歴のどれでも、「1 件の出来事につき 1 件の通知」という同じ形に揃う。
- 番組名の食い違いは、その放送回の通知に添えれば、日ごとのまとめより早く、文脈付きで分かる。
- 「止まったら知らせる」は、止まった本人ではなく外から見る方が確か。監視の仕組みを持つ人は、すでにある仕組み（Prometheus のアラートなど）で足りる。
- 監視との約束をメトリクスの名前に置けば、人が読むログの文言を直しても、監視が黙って外れない。

## 検討した案

- 日ごとのまとめ（毎朝 1 通、前日の結果・再試行待ちの一覧・番組名の食い違い）を主にする。届くこと自体が生存確認を兼ねるが、通知先が壊れたときは何も届かず、それに人が気づくことに頼る。
- 日ごとのまとめと都度の通知を両方出す。量が増え、2 つの形が並ぶ。
- ログの文言を条件に、ログ基盤でアラートを作る。rajikura のコードは変えずに済むが、ログの文言が監視との約束を兼ねる。
- 定期的に外の URL を叩く heartbeat（healthchecks.io など）。Prometheus を持たない人には効くが、要望を見てから足す。

## 帰結

- 1 日に録る本数が多い人のために、録音済みの通知だけを `notify.success = false` で通知先に送らないようにできる。止めても Web UI の履歴には残る。異常は止められない。
- 再試行待ちは通知しない（ふつうに起きることで、期限が近づけば期限間近が出る）。
- 監視の仕組みを持たない人は、プロセスが落ちたことに rajikura からは気づけない。コンテナやサービスの再起動の設定と、Web UI が開けないことで気づく。通知先が壊れたことは Web UI の帯で分かる（[ADR 0011](0011-notifications-written-to-db-then-delivered.md)）。
