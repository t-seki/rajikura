# 人が読み書きする口では、放送回の時刻を放送日の時刻で書き、出来事の時刻を暦の時刻で書く

## 決定

時刻は、何の時刻かで書き分ける。

- 放送回の時刻（開始・終了と、放送の中の時刻）は、その放送回の放送日と、放送日の時刻（05:00〜28:59）で書く。
- rajikura の中で起きる出来事の時刻（試行、録音期限、保存のやり直しの期限、残す期限、通知の日時など）は、暦の時刻（暦の日付と 0〜23 時）で書く。

形:

- 範囲は人が読み書きする口すべて（Web UI、通知の本文、ジョブの失敗の理由に出るエラー文）。ログと API・DB は外す。API・DB は `00:00〜23:59` と RFC 3339 のままで、放送日の時刻は値の型にせず、人が読み書きする口の中で変換する。
- 毎週の予約の開始時刻は、Web UI の予約のフォームで `05:00〜28:59` だけを受け付ける。曜日は放送日の曜日で数える。
- 放送回の時刻は、その放送回の開始の放送日を基準に数える。終わりの時刻や放送の中の時刻（ライブ録音の欠けた区間）も、開始と同じ放送日で数え、29:00 を越えてよい（4:30〜5:30 は `28:30〜29:30`）。
- 放送日がすぐ近くに出ていないところは、放送日を添える（番組表の詳細パネルの `10/20(火) 27:40〜28:00`）。ジョブの詳細・通知の本文のように放送日がもう出ているところは、時刻だけを書く（`27:40〜28:00`）。
- ライブ録音の次の試行（放送回の開始）や録音期限（放送の終了の 5 分後）のように、放送回から決まる出来事の時刻も、出来事なので暦の時刻で書く。
- 番組表の今の時刻の札は、放送日の軸の上の位置を指すので、放送日の時刻で書く（1:32 なら `25:32`。グリッドの時刻の列の `25時` と揃える）。

## 理由

- 毎週の予約の曜日は放送日の曜日なので、深夜の放送を `00:00〜04:59` で書くと、暦の曜日のつもりで書いた人の曜日が 1 日ずれる（「月曜の深夜 1 時」を `月 01:00` と書くと、火曜の 1 時になる）。`05:00〜28:59` だけを受け付ければ、この取り違えが起きない。
- 何と一緒に出すかで書き方を決めると、同じ放送回が、番組表では `10/20(火)` の `27:40`、詳細パネルでは `10/21(水) 03:40〜04:00` と 2 通りに書かれる。何の時刻かで決めれば、放送回の時刻はどこでも同じに書かれる。
- 出来事の時刻は、放送日に属さない。ジョブの一覧の同じ「次の試行」の列が、ジョブによって暦の時刻と放送日の時刻に分かれないように、全部暦の時刻にする。
- 保存の形はアトミックな値のままにしておき、人が触る口で見せ方を変える。

## 検討した案

- `00:00〜04:59` と `24:00〜28:59` の両方を受け付ける。保存する値は同じでも、書いた人がどちらのつもりかを区別できず、曜日の取り違えを止められない。
- 時刻を何と一緒に出すかで決める（放送日に添えて時刻だけを出すところは放送日の時刻、暦の日付を持つ日時は 0〜23 時）。上の理由で、同じ放送回が 2 通りに書かれる。
- 放送回から決まる出来事の時刻（ライブ録音の次の試行・録音期限）も放送日の時刻で書く。ジョブの一覧の同じ列で書き方が混ざる。
- Web UI だけに掛ける。通知の本文の一部だけが暦の時刻で書く、という割れ方が残る。
- API と DB も放送日の時刻にする。保存の形を人の見せ方に合わせる理由が無い。

## 帰結

- ジョブの詳細では、放送回の `27:40〜28:00` と、次の試行の `10/21 03:40` が並ぶ。同じ瞬間でも、放送回の時刻か出来事の時刻かで書き方が違う。
- 放送日の書き方（`10/20(火)` と `2026-10-20`）は揃えていない。
