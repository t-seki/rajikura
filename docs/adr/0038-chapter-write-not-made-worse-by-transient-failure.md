# チャプターは音声を取り直さず、保存したファイルに書き込む。書き込みの前の取得が一時的に失敗したら書かず、取り直しは待ちを残してやり直す

## 決定

[ADR 0033](0033-chapters-written-into-saved-file.md) を置き換える。チャプターの取り直しでファイルにチャプターを入れるとき、radiko から音声を取り直さず、保存したファイルにチャプターだけを書き込む。人が指示して同じ書き込みをさせる操作（チャプターの入れ直し）を持つ。チャプターの取り方と形、設定 `chapters`、保存のときに待つかの決め方、待っている間に API を引く間隔と打ち切り、ジョブの印（入った・待っている・入らなかった）は [ADR 0027](0027-chapters-refetched-by-rerecording.md) のまま。ADR 0033 から変えるのは、書き込みの前に保存した放送回のチャプターを取り直したとき、一時的に取れなかった放送回があった場合の扱い（下の「書き込みの前の取得」）。

書き込み:

- 保存したファイル（ジョブの保存先）を読み、チャプターだけを入れて書き直す。音声・タグ・画像はファイルのまま残す。番組表から付け直さない。
- 設定 `muxer` に従う。`builtin` は rajikura が書いた m4a を読む部品を持ち、`ffmpeg` は ffmpeg でチャプターだけを移す（`-map_chapters` と `-c copy`）。どちらも ADR 0027 と同じ形（`chpl` とチャプタートラック）を書く。
- 同じフォルダの partial に書き、書いたファイルの音声のサンプル（数とバイト列）が元のファイルと一致することを確かめてから、rename で置き換える。どこかで失敗したら partial を消し、元のファイルを残す。保存先にファイルが無ければ書かない。置き換えたら、保存のときと同じくメディアサーバーに再スキャンを頼む。
- 連結したファイルでは、2 つ目以降のパートのチャプターを、前のパートの長さだけずらす。パートの長さは保存のときに DB に残し、残っていない（ADR 0033 より前に保存した）ファイルでは、番組表の放送時間（終了 − 開始）で代える。
- 書き込みの間も、ジョブは録音済み（`done`）のまま。試行を起こさず、試行回数・欠落の印・保存先は変えない。
- 書き込むのは録音のループだけ（保存先のファイルを書く者を 1 つに保つ）。
- 書き込みのたびに、ジョブのチャプターの書き込みの履歴に 1 行残す（時刻、誰が（チャプターの取り直しかチャプターの入れ直しか）、結果（書き込んだときはチャプターの件数、取れなかったので書かなかった、失敗したときは理由））。試行の履歴とは別に、ジョブの画面・API・CLI に出す。失敗しても通知はしない。音声のサンプルが元と一致しなかったときは、ログに Error で出す。下の書き込みのやり直しで書かなかった回は、書き込みに数えず、履歴に残さない。

書き込みの前の取得:

- 書き込むたびに、保存した放送回（欠落を除く）のチャプターを radiko から取り直し、ファイルのチャプターをその結果で置き換える。
- 取れていたはずの放送回が、取り直しで一時的に取れなかった（404 か、通信の失敗・読めない応答。ADR 0027 で「まだできていないかもしれない」に分けるもの）ときは、ファイルに書かない。置き換えると、ファイルに入っていたその放送回のチャプターが消えるか、取れるようになったチャプターが入らないため。取れていたはずの放送回は、チャプターの取り直しとチャプターの入れ直しで分ける（下の各節）。
- 取れていたはずの放送回のほかで取れなかった放送回と、待っても入らない（空か、放送回の一覧に eventId が無い）放送回は、チャプター無しにし、取れた分を書く。

チャプターの取り直し（自動）:

- 待っていた放送回が全部取れるようになったら（打ち切りの時点で一部だけ取れるようになっていれば、そのとき）、保存したファイルに書き込む。
- 取れていたはずの放送回は、保存のときに待たなかった放送回（取れたか、待っても入らない）と、待っている間に取れるようになった放送回。打ち切りの時点でまだ取れるようになっていない放送回は含めず、取り直しで取れなければチャプター無しにする。
- 書き込みの前の取得で、取れていたはずの放送回が一時的に取れなかったら、書かずに待ちを残す（書き込みのやり直し）。ジョブの印は待っているのまま、待っている放送回の様子も変えない。次の見回り（待っている間に API を引く間隔の後。上限を過ぎるなら上限の時刻）に、もう一度書き込みに入る。書かなかったことはログに出す。
- 書き込みのやり直しは、打ち切りの後、待っている間の打ち切りと同じ長さ（6 時間）まで（最後の放送回の終了から 12 時間）。上限を過ぎた書き込みでも、取れていたはずの放送回が一時的に取れなかったら、書かずに諦める。ファイルは前のまま、書き込みの履歴は取れなかったので書かなかった、ジョブの印は入らなかったにする。
- 録音期限を過ぎたら、やり直しの途中でも待つのをやめる（ADR 0027 の待つかの決め方のまま）。
- 書き込めても書き込めなくても通知しない。打ち切りも、やり直しを諦めたことも通知しない。

チャプターの入れ直し（人）:

- 入口は API・CLI（`rajikura chapters`。ジョブ 1 件の指定と、まとめて当てる `--all`）・Web UI のジョブの画面のボタン。API は DB のジョブに頼みを書いて録音のループを起こし、受け付けたことを返す。書き込んだ結果は、ジョブの印とチャプターの書き込みの履歴に出る。
- 当てられるのは、タイムフリーから録った録音済みのジョブ。ライブ録音のジョブは断る。
- `--all` は、印が「取りに行っていない」か「入らなかった」のジョブに当て、「入った」「待っている」は飛ばす。放送日では絞らない。ジョブ 1 件の指定なら、「入った」のジョブにも当て、ファイルのチャプターを置き換える。
- 設定 `chapters` がオフでも行う。
- 取れていたはずの放送回は、印が入ったのジョブ（ファイルに全部の放送回のチャプターが入っている）の、保存した全部の放送回。入ったのジョブで、書き込みの前の取得で一時的に取れなかった放送回があれば、ファイルは書かない（取れなかったので書かなかった。印は入ったのまま）。やり直さず、チャプターの待ちも起こさない。頼みは済んだものとして消す。
- それ以外のジョブ（印が値なし・入らなかった・待っている）は、一部の放送回だけ取れたら、取れた分を書き込む。1 つも取れなければ、ファイルは書かない。チャプターの待ちは起こさない。
- 印は ADR 0027 の決まりで付け直す（それまで印の無かったジョブにも付く）。
- 通知はしない。

## 理由

- 2026-11-02、録り直しで取り直した音声が「配信を停止しています」のアナウンスに差し替わり、前のファイルを上書きして失った（#37）。チャプターの取り直しも同じく音声を取り直して上書きするので、同じことが起きうる。チャプターは音声から作っておらず API から取るので、音声を取り直す理由が無い。
- 音声を取り直さなければ、チャプターのある局でほぼ全部の放送回の音声を 2 回取ることも無くなる（ADR 0027 の帰結）。
- AI のチャプターを入れる前に録ったファイルにも、後からチャプターを入れたい。2026-11-02 にチャプターの API を局（LFR・TBS）と放送日で引いたところ、2026-04-15 以降の放送回はほぼ全部取れ、2026-03-01 以前は全部 404、2026-04-01 は一部だけ取れた。境目は radiko が公表しておらず、局や時期で変わりうるので、放送日で絞らず API に任せる。
- 既定の `muxer` は `builtin` なので、builtin で書き込めないと既定の設定で使えない。読むのは rajikura が書いた m4a だけで足りる。両方で同じ形を書けば、箱を比べるテスト（[ADR 0013](0013-builtin-m4a-muxer.md)）を保てる。
- 音声のサンプルの一致を毎回確かめれば、書き込みの不具合で音声を壊したファイルが元を置き換えることは無い。
- 書き込みは数秒で終わるので、録音の試行に乗せる理由が無い。録音済みのままにすれば、取り直しの間に番組表に録音予定と出ることも無くなる。
- 書き込む者を録音のループ 1 つにすれば、録り直しの試行と同じファイルを同時に書くことが無い。人の操作も、録り直し・手動再試行と同じく DB に書いてループを起こす形になる。
- タグ・画像を付け直さないのは、番組表の値が録ったときから変わりうるため（番組名の変更など）。
- 書き込みの失敗を通知しないのは、元のファイルが残り、聴けなくなるものが無いため。ファイルが消えている・書けないことは人が知るべきなので、ジョブに残して見せる。
- 試行を起こさないので、試行の履歴には残らない。いつ・何件入ったか・なぜ入らなかったかを後から確かめられるよう、書き込みの履歴を別に持つ。
- 連結したファイルのパートの長さを番組表で代えると、数秒ずれうる。飛ぶ先として困ることはほぼ無く、分割番組だけ入らないよりよい。
- ADR 0033 では、書き込みの前の取得が一時的に失敗すると、待ちが消えて入らなかったになり、後から見回らなかった（#45。PR #43 のレビューで見つかった）。一部だけ失敗したときは、ファイルに入っていたチャプターが取れた分に置き換わって減った。ADR 0027 の取り直しの試行には再試行があったが、ADR 0033 で試行に乗せなくなったときに、代わりのやり直しを決めていなかった。
- 一時的に取れなかったかの分け方は、保存のときに待つかの分け方（404 と通信の失敗・読めない応答を、まだできていないかもしれないに分ける。ADR 0027）を使い回す。一度取れた放送回が 404 を返すのは、まれな一時的な返事として扱う。
- やり直しで待ちを残せば、待っている間の印と見回りをそのまま使え、DB の表や列が増えない。やり直しの上限に待っている間の打ち切りと同じ長さを使えば、新しい値も DB の列も要らず、radiko が数時間落ちていても間に合う。
- 上限を過ぎても取れた分を書かないのは、ファイルを前より悪くしないため。人はチャプターの入れ直しで後から入れ直せる。
- 取り直しで、打ち切りの時点でまだ取れるようになっていない放送回を取れていたはずの放送回に含めないのは、含めるとその放送回が 404 を返し続ける限り、取れるようになった放送回のチャプターまで入らなくなるため（ADR 0033 の、打ち切りの時点で一部だけ取れていれば書く決まりを保つ）。どの放送回が待たなかったか・取れるようになったかは、待っている間の様子として DB に残っているので、DB の表や列は増えない。
- チャプターの入れ直しは人が頼み直せるので、やり直しは足さない。ファイルを前より悪くしないことだけは、ファイルに全部の放送回のチャプターが入っていると分かる入ったのジョブで取り直しと揃える。値なし・入らなかったのジョブまで止めると、チャプターの API が 404 を返す古い放送回（2026-03-01 以前）を含む連結したファイルに、取れるパートの分も入れられなくなる。

## 検討した案

- 今のまま、音声を取り直して上書きする（ADR 0027）。#37 と同じく、取り直した音声が差し替わっていれば前のファイルを失う。
- チャプターの取り直しをやめ、人がまとめて流すチャプターの入れ直しだけにする。保存のときにまだチャプターができていなかった放送回（終了から 1〜2 時間はよくある）に、人が流すまで入らない。
- 書き込みを ffmpeg だけで行う。既定の `builtin` で使えない。
- 人の操作を HTTP のハンドラがその場で書き込む。結果をすぐ返せるが、保存先のファイルを書く者が 2 つになり、録り直しの試行と同時に同じファイルを書きうる。
- 古いジョブを、今のチャプターの待ちに入れるだけにする。部品は増えないが、待ちの打ち切り（最後の放送回の終了から 6 時間）がすぐ効くので、古いジョブだけの例外が要る。
- 連結したファイルを対象から外す。分割番組だけチャプターが入らず、取りこぼしに見える。
- 書き込みの失敗を通知する（新しい通知の種類）。元のファイルが残っていて、人にすぐ何かしてもらう出来事ではない。
- 書き込みを試行の履歴（`attempts`）の 1 行として残す。入手・検証・保存の段階や長さの値が当てはまらず、空の列が並ぶ。
- 書き込みの記録をログだけにする。いつ入ったか、なぜ入らなかったかを、ジョブの画面で確かめられない。
- 書き込みのときに、タグ・画像も今の番組表から付け直す。録ったときと違う値に変わりうる。
- 書き込みの前に取り直さず、待っている間に取れたチャプターを使い回す。待っている間に手元にあるのは、その回に引いた放送回の分だけで、前の回に取れるようになった放送回や保存のときに取れた放送回の分は残っていない。使い回すには、チャプターの中身を DB に持つか、ファイルから読み戻す部品が要る。
- 書き込みの前の取得の中で、その場で数回再試行する。録音のループが止まる時間が延び、radiko が数分より長く落ちているときには効かない。
- 通信の失敗・読めない応答だけを一時的な失敗にし、404 は含めない。保存のときに待つかの分け方と食い違い、分け方が 1 つ増える。
- やり直しを録音期限まで続ける。新しい値は要らないが、ある放送回が 404 を返し続けると、期限まで 30 分ごとに引き続ける。
- やり直しを回数で数える。DB に回数の列が要る。
- 上限を過ぎたら、取れた分を書く（ADR 0033 の振る舞い）。ファイルに入っていたチャプターが減りうる。
- やり直しで書かなかった回も、書き込みの履歴に 1 行ずつ残す。最大で十数行の「取れなかったので書かなかった」が並ぶ。印が待っているのままなので、待っていることは画面で分かる。
- チャプターの入れ直しでも、頼みを残して次の見回りでやり直す。入れ直しは待ちを起こさない決まりで、人が頼み直せる。
- 取り直しで、保存した全部の放送回を取れていたはずの放送回にする。打ち切りの時点で一部だけ取れるようになっていても、残りが 404 を返し続ける限り書けず、上限で諦める。
- チャプターの入れ直しで、どのジョブでも、一時的に取れなかった放送回があれば書かない。古い放送回を含む連結したファイルに、取れるパートの分も入れられなくなる。
- チャプターの入れ直しで、ファイルからチャプターを読み戻し、取れなかった放送回の分を残して足し合わせる。ファイルのチャプターを読む部品が要る。

## 帰結

- チャプターのある局でも、音声を取るのは 1 回になる。録音が非会員の聴取制限に数えられるかの心配（ADR 0027 の帰結）は、チャプターについては無くなる。
- 終了の数分後に置かれたチャプターの無いファイルが、後で同じパスのチャプター付きのファイルに置き換わるのは ADR 0027 と同じ。先にファイルを取り込んだプレイヤーが追いつくかは確かめていない。
- チャプターの入れ直しで、それまで印の無かった古いジョブにも印が付き、取れなかったものは Web UI の一覧に「チャプターなし」と出る。
- 連結したファイルのうち、ADR 0033 より前に保存したものは、2 つ目以降のパートのチャプターが数秒ずれうる。
- 書き込みのやり直しの間、ジョブの印は待っているのままで、最後の放送回の終了から最長 12 時間待っていると出る。
- 打ち切りの 30 分（待っている間に API を引く間隔）前より前に始まった書き込みのやり直しで、待っていた放送回が打ち切りまで取れないままだと、打ち切りの時点で諦めて入らなかったになる（ファイルは前のまま）。やり直しの間は待ちの様子を変えないので、次に引く時刻が打ち切りより後かどうかでやり直しの間と見分けており、やり直しを始めた時刻の 30 分後が打ち切り以前になるやり直しは、次に引く時刻が打ち切りを超えない。打ち切りの 30 分前より後に始まったやり直しは、次に引く時刻が打ち切りより後になるので、上限（12 時間）まで続く。やり直しの次の時刻を打ち切りの後に寄せる案は、打ち切りまでの再試行を止めるので採らなかった。
- 一度取れた放送回が、radiko の側でチャプターを消されて 404 を返し続けると、やり直しの上限まで書き込めず、入らなかったになる。ファイルのチャプターは前のまま残る。
- 待っても入らない（空・eventId が無い）に変わった放送回は、取り直しでも入れ直しでも、ファイルからその放送回のチャプターが消える（ADR 0033 のまま）。
- 入らなかったのジョブのファイルに一部の放送回のチャプターが入っているとき、入れ直しでその放送回が一時的に取れなければ、その分はファイルから消える（ADR 0033 のまま）。
