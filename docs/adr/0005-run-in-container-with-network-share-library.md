# 常駐はコンテナを主にし、ライブラリへはネットワーク越しの共有に書く

## 決定

rajikura の `serve` を常駐させる主な形は、コンテナにする。イメージは ghcr.io に public で置き、誰でも認証なしで pull できる。git のタグ（`v0.1.0` など）を打つとビルドする。

- データのフォルダ（DB・秘密の鍵のファイル・作業用フォルダ）は、コンテナの `/data` に、コンテナの外に残るボリュームとして置く。
- ライブラリ（`/library`）は、メディアサーバーが読むフォルダを、ネットワーク越しの共有（NFS・SMB など）でマウントして書いてよい。
- 書き込める範囲は、rajikura が書くフォルダだけに絞るのを勧める。メディアサーバーが読む側は、読み取り専用のままでよい。

## 理由

- 要件で、コンテナイメージを主な配布形態にすると決めている（[要件定義](../requirements.md)）。コンテナ基盤なら、再起動・ログの集約・版の上げ下げを基盤に任せられる。
- 録音を置くライブラリは、メディアサーバーと同じ NAS などにあることが多い。ライブラリをネットワーク越しに書ければ、rajikura を別のマシンで動かせる。
- 書き込める範囲を 1 つのフォルダに絞れば、ほかの録音や音楽を壊さない。
- ソースを公開しているので（[ADR 0028](0028-publish-as-oss-under-radiko-terms.md)）、イメージを非公開にする理由が無い。

## 検討した案

- Linux では、バイナリを置いて systemd で常駐させる形を主にする。共有のマウントやログの扱いを、使う人がマシンごとに組むことになる。Linux のバイナリは配るが、systemd の定義は持たない（Windows のサービスは [ADR 0020](0020-windows-service-with-virtual-account.md)）。
- ライブラリが入っている既存の共有を、そのまま読み書きにする。メディアサーバーの読み取り専用の線を崩し、書き込める範囲も広い。
- イメージを private にする。pull する側に資格情報が要るだけで、ソースを公開しているので守るものが無い。

## 帰結

- ライブラリをネットワーク越しに書くと、メディアサーバー（Jellyfin）のリアルタイム監視が効かない。そのために、保存のたびにライブラリの再スキャンを頼めるようにしている（`internal/jellyfin`）。
- radiko のエリアの判定は、コンテナの外向きの通信の出口の IP で決まる。経路が変わってエリアの外と判定されたら、通知で知らせる。
- 新しい版を動かすには、タグを打ってイメージを作り、動かしている側のイメージの版を上げる。
