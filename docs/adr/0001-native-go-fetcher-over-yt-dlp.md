# 音声の入手は yt-dlp を使わず Go で行う

## 決定

radiko の認証（auth1 / auth2）と、タイムフリーの音声の入手は、rajikura が Go で行う。yt-dlp は使わない。

- 入手は 300 秒ずつのチャンクに分け、各チャンクのプレイリスト（マスタ → medialist）を読んで、ADTS のセグメントを順に取ってつなぐ。
- 外部のプログラムにはネットワークを触らせない。m4a への格納は、手元の ADTS からファイルを作る段だけで、その作り方は [ADR 0013](0013-builtin-m4a-muxer.md) にある。
- 継ぎ目は `#EXT-X-PROGRAM-DATE-TIME` で確かめる。

## 理由

- yt-dlp 本体の radiko の extractor は、この決定のとき、ログインにもタイムフリー30 にも対応しておらず、radiko 側のプレイリストの変更にも追随していなかった。
- 更新が続いているプラグイン（yt-dlp-rajiko）は、Python への依存を増やすうえ、スマホアプリの鍵や位置情報を偽ってエリアの外の局を取る機能を含む。rajikura はエリアを偽らない（[ADR 0028](0028-publish-as-oss-under-radiko-terms.md)）。
- 入手を Go に置けば、タイムアウト・再試行・トークンの失効を 1 か所で扱える。

## 検討した案

- yt-dlp で取り、壊れたら自前の認証と ffmpeg に切り替える。上の理由で、主な方式にできるものが yt-dlp に無い。
- 取得を ffmpeg に任せる（HLS の URL を ffmpeg に渡す）。タイムアウトや失効の扱いが子プロセスの中に入り、継ぎ目を確かめられない。

## 帰結

- 各チャンクの `end_at` と `to` は「seek + l」にする（l は 5〜300 秒）。番組の終了時刻のままだと medialist に `#EXT-X-ENDLIST` が付かず、入手が等速のライブの扱いになる。
- 長さの検証は、書いた m4a の長さと、全セグメントの `#EXTINF` の合計の差で見る。
- 入手の方式は差し替えられる形にしておき、ほかの方式を予備として後から足せる。
- エリアの外の局は、エリアフリー会員の正規のログインでだけ取る。位置情報やエリアの偽装は実装しない。
- radiko 側の変更（ホストの移行など）に追随する保守は、rajikura の仕事になる。
